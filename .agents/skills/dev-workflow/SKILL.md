# 墨账开发工作流

> 来源：《项目复盘/03_开发工作流.md》——18 天 52 个版本节点实际跑通的流程。
> 本文件是用户级通用版 `dev-workflow`（`~/.agents/skills/dev-workflow/`）的**墨账实例化**：同名 skill 项目级优先于用户级生效，故在墨账内走本文件；改流程骨架先改通用版，再同步到这里。
> 三条底色：**小步、可验证、留记录**。"AI 说改完了"不算数，六道关全过才算数。
> 项目约定（技术红线/已知坑/设计系统）以 `AGENTS.md` 为准，本文件只管"流程怎么走"。

## 第 1 步｜需求澄清 + 方案分诊

- 先用一句"给谁解决什么问题"复述需求；说不清就先问用户，不要靠猜动手。
- 分诊三列写下来（最常被跳过、也最不能省）：
  1. **能用的方案** → 本次实施；
  2. **用不上的方案及原因** → 防止照搬引入用不上的复杂度；
  3. **暂时不做及原因** → 写进文档"边界与后续"。
- 涉及 AI 产出或数据落盘的功能，先列"最坏情况"（连点、重复提交、中途切账本、隔很久才确认），每条最坏情况变成一条可测断言。参考先例：AI 只产草稿不落盘、入账走与手动记账完全相同的链路。
- 接手"改动已经写完"的半途任务时，第 1–3 步缺了就补：至少补出需求复述与分诊记录，再进自检。

## 第 2 步｜先读代码再改

- 改 `js/app.js`（1400+ 行）前必读文件头部结构注释，定位要动的分区。
- 动手前必须能回答："这次改动会连带影响哪几处？"答不出就继续读。
- 对照 `AGENTS.md`「已知坑」检查相关项：clip-path 会裁剪内部弹出层、同名工具函数（esc/uid/toast）在多个 IIFE 有副本需同步改、python replace 找不到目标会静默跳过等。

## 第 3 步｜小步实施

- 一次改动控制在"能一句话描述"：加一个字段、改一处颜色、修一个错位。
- 一次只解决一件事。过程中发现的新问题记下来，另开一轮流程；只有一行内的连锁修复才顺手带上。
- 遵守技术红线（详见 AGENTS.md）：零依赖无构建无 npm、存储 key `jigong_` 前缀、IIFE + `window.JG.*` 跨模块通信、设计系统四条硬规则（主操作 `.btn.primary` 金牌墨字、金额宣纸金线块、表面只用暖纸色系、墨青选中/朱砂警示/金色主操作严格区分）。

## 第 4 步｜三重自检（改完立刻跑）

| 检查 | 手段 | 过关标准 |
|---|---|---|
| 语法 | `node --check js/xxx.js`（改过的每个 js；纯 CSS/HTML 改动无对象，此关跳过） | 无报错 |
| 数据逻辑 | 涉及存储/迁移/算钱：`node tests/run-tests.js` | 全部断言通过 |
| 页面健康 | `node server.js` → 浏览器开 http://127.0.0.1:8787 与 smoke.html | smoke 断言全绿；控制台 `window.__errors` 为空（CSS/HTML 改动以此关代替语法检查） |
| 结构审计 | 大段 HTML/CSS/JS 编辑后 grep 关键定义（如 `API_PRESETS`、`function toast`、`window.JG`） | 定义幸存、无多余 `</div>`、main 未提前闭合 |

- UI 改动要在浏览器里按用户路径实际走一遍：功能对、数字对、手感对。AI 可用浏览器自动化工具验证；无法自动化时明确请用户手验，文档状态标 🔄 已完成待验证（用户确认后再改 ✅）。凡视觉质感、动效手感这类无法自动断言的项，自动化通过也只能标 🔄。
- localStorage 结构变化：必须写 migrate 函数 + 保留旧键备份，并跑数据测试。

## 第 5 步｜写记录：带日期的文档

**选文件夹**（按"最主要的那一类"归，顺带改的写进文档正文）：

| 改动性质 | 去处 |
|---|---|
| 能跑但结果/显示/体验不对 | bug修复文档 |
| 报错、崩溃、接口失败 | 错误修改文档 |
| 已有功能的调整/优化/美化 | 功能修改文档 |
| 从零新增的功能模块 | 新功能开发文档 |

- 命名 `YYYY-MM-DD_标题.md`；单篇 ≤300 行，超了拆 `标题-1.md`、`标题-2.md` 并逐一登记、标明阅读顺序。
- 打开目标文件夹的「目录.md」，里面有该文件夹的登记规则与文档模板，按模板写（各文件夹字段略有差异）。正文核心内容固定包含：缘起/背景、实现、验证（断言与实测结果）、涉及文件、边界与后续——**没做的和永远不做的也要写明**。
- 过关标准：三个月后回看，能知道当时为什么这么改。

## 第 6 步｜登记 + 版本 + 提交

1. 目标文件夹「目录.md」登记表加一行：日期 / 文档链接 / 一句话说明（含版本号与缘起）/ 涉及功能 / 状态。
2. 更新 `开发文档导航.md`：顶部"当前版本"换成新版本号；「本版本记录」表最上面插入一行（版本/日期/主要改动/关键文档链接）；够分量的改动在「项目里程碑」补一行。
3. 版本号（从导航文档顶部当前版本往下走）：**minor 仅限"从零新增的功能模块"**（对应新功能开发文档，如 V0.15.5→V0.16.0）；bug 修复/调整优化一律 patch+1（如 →V0.15.6）；不动应用代码的纯工具/文档类改动不升版本。
4. `git commit`，信息格式：`V0.x.y 标题：改了什么（为什么/用户要求）`。一次流程一个提交。

## 收尾核对（向用户报告"完成"前逐条过）

- [ ] 需求一句话能复述；分诊三列有记录
- [ ] `node --check` 全过；数据类改动跑过 `node tests/run-tests.js`
- [ ] 冒烟全绿、`window.__errors` 为空（或已请用户手验、状态标 🔄）
- [ ] 文档已写入正确文件夹并登记「目录.md」
- [ ] `开发文档导航.md` 版本号与版本表已更新（或注明不升版本的原因）
- [ ] 提交信息 = 版本号 + 改了什么 + 为什么
