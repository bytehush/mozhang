# [2026-09-13] 书架翻开转场重编排：引入 GSAP timeline 修复割裂感

- 类型：功能修改（动效优化，响应用户反馈）
- 上线版本：V0.13.1
- 状态：✅ 已完成并验证

## 一、用户反馈

1. **翻开动画好奇怪**——建议参照 GSAP 找类似动画；
2. **衔接不连贯**——像剪辑里没做好的转场。

## 二、病因诊断（为什么怪）

1. **翻过了头**：封面 rotateY(-148°)，超过 90° 后观众看到的是封面的**空背面**
   （没有做背面内容），视觉上像"卡片翻走消失了"，而非"翻开书"；
2. **三段硬切**：封面翻开(450ms) / 书架退场(300ms) / 工作台浮现(480ms) 各自独立、
   起止不重叠，切换点生硬——正是"转场没做好"；
3. **运动方向矛盾**：翻开是横向运动，工作台却从底部纵向浮起，方向断裂。

## 三、解法：引入 GSAP（本地 libs，同 Chart.js 模式）

- `libs/gsap.min.js`（3.12.5，72KB，本地文件离线可用，无 npm/CDN 在线依赖）；
- GSAP 的价值不在"动画更多"，而在 **timeline 编排**：多段动画精确重叠、统一缓动、
  单一完成回调——这正是转场（match cut）需要的。

## 四、新转场编排（剪辑语言：全程"向前推近"一个方向）

**翻开**（总时长约 1.0s，段段重叠）：

| 时刻 | 段落 | 运动 |
|---|---|---|
| 0s | 封面掀开 | rotateY 0→**76°**（不过 90°，永远看不到空背面）+ 微放大，power2.in |
| 0.10s | 邻卡先散 | 其余封面淡出缩小 0.94 |
| 0.28s | 镜头推近 | 书架整体 opacity→0 / scale→1.07（向前推进） |
| 0.58s | 交棒 | 书架隐藏、工作台就位（初始 opacity 0 / scale .965 / y 12） |
| 0.60s | 内页浮现 | 工作台推近到位，power3.out——延续"向前"方向 |

**返回书架**：反向——工作台拉远淡出（scale 1.03）→ 书架从推近中归位（scale 1.05→1）。

配套清理：`.bs-inner` 的 transform 过渡移除（避免与 GSAP 逐帧赋值打架，hover 上浮
移交外层 .bs-card）；旧 CSS 转场类（.bs-card.opening / .opening-stage / page-enter）
删除；结束后 `clearProps` 清理内联样式，保证反复翻开无残留；REDUCED / GSAP 缺失
自动回退为直切。

## 七、补记（同日）：翻开方向修正

用户反馈"做成向内翻阅了，应该向外反翻阅"。原 rotationY: 76（正角度）绕左缘
把封面往书架深处倒=向内翻；改为 **rotationY: -76（负角度）**，右缘朝观众方向
掀出来=向外翻开。已用 GSAP 内联值验证（动画中途 rotateY(-18.3°)，负向进行中）。

## 八、补记（同日）：非线性节奏

用户反馈"动画速度可以用非线性动画"。全面更换缓动曲线（原来 power 系偏匀速感）：

- **封面掀开加"预备动作"**（动画十二原则 anticipation）：先向反方向轻压
  rotationY +5°/scale .985（0.11s power1.in），再 **-78° 越掀越快**（0.42s power3.in）；
- 邻卡散开：expo.out（瞬间散开缓缓停）；
- 书架推近：power3.in（加速冲向观众）；
- **工作台落定：back.out(1.2)**（轻微过冲回弹，有"放下一本账"的分量感）；
- 返回：工作台拉远 power2.in，书架归位 back.out(1.1)。

实测（后台测试环境用 setInterval 手动驱动 GSAP 全局时间线绕开 rAF 停摆）：
翻开轨迹 -3°→-78° 证明"先慢后快"，工作台/书架切换与回弹落定均正确，
全程零报错。注：GSAP ticker 走 rAF，后台标签页会冻结、回前台自动补完，
前台使用无感知。

## 九、补记（同日）：容器变换转场——封面扑面放大，返回缩回归位

用户反馈：点击账本后要有**放大动画**（非线性），返回就是反过来。采用
Material Design"容器变换"（container transform）语言，重写两条 timeline：

**翻开（总约 1.5s）**：预备轻压 → 掀开 -78° → 邻卡散 → **封面以 -40° 翻开姿态
扑面放大到铺满视口**（scale→blowScale，按视口/卡片尺寸动态计算 ≈8-9 倍，
power3.in 越放越快）→ 放大末段渐隐 → 工作台以 back.out(1.15) 落定；
**返回**：工作台淡出 → 当前账本封面**从铺满缩回卡片原位**（scale 9.3→1，
power3.out 越缩越慢）→ 其他封面淡入。

工程三要点（本轮踩坑）：

1. **并发守卫**：模块级 shelfTl 保存进行中的转场，新转场开始前 `progress(1)`
   强制完成旧的——翻开/返回快速连点、后台节流导致 timeline 滞后时都不会互相打架
   （此前两条 timeline 的 onComplete 交错执行，书架 hidden 被迟到的翻开回调藏回去）；
2. **tween 预声明，禁在 add 回调里动态 add**：动态插入的 tween 的 startTime 以
   插入时刻计，若时间线被外力推进（时间跳跃/将来改动）会排到永远播放不到的位置，
   状态卡死。改为预声明 + **函数式目标值**（blowScale() 在 tween 首次渲染时求值，
   此时书架已显示、rect 有效）——任何时间跳跃下状态都收敛；
3. 尺寸自适应：blowScale 按 `max(vw/卡宽, vh/卡高)×1.15` 动态计算，不同窗口都铺满。

验证（时间跳跃法断言终态，三轮全绿）：翻开→工作台/书架隐藏/样式干净 ✓；
返回→书架重现/封面 scale 9.3→1 归位/全部卡片可见 ✓；跨账本再翻开 ✓；零报错 ✓。

## 十、补记（同日）：节拍分离——掀开与放大不再同步

用户反馈"打开动画和放大动画是同步的"。病因：掀开用 power3.in（越掀越快），
大半动作被压到该段结尾，紧接着扑面放大就开始——两段视觉上糊成一团。

改法（节拍/beat 分离）：
1. 掀开改 **power2.out**（先快后缓）——翻开动作一眼看清，0.44s 完成；
2. **定格一拍**（0.18s）：封面以 -78° 悬停，邻卡未散、书架未退——画面是
   "一本翻开的书立在书架上"，给观众读帧时间；
3. 然后邻卡散 + 扑面放大 + 书架退场同步推进（"进入"段）→ 化作记录表。

逐帧验证（暂停全局时间线手动 scrub）：0.45s 处封面 -78°/1.06 且邻卡可见
（定格成立）；0.85s 处放大进行中、邻卡淡出（进入段成立）；终态正确、零报错 ✓。

## 十一、补记（同日）：节拍加强——0.16s 的停顿肉眼看不见

用户复查后反馈"没有同步，还是跟之前一样"——第一节拍分离（0.16s 定格 +
power2.out 缓动尾）**在真实观感里几乎无法察觉**，掀开与放大依然读作一坨。

改法（把三拍拉开到可辨识的时长与质感）：

1. **掀开带"啪嗒"过冲**：掀开段改 `back.out(1.2)`——封面越过 -78° 少许再回稳，
   读作"封面被掀开并拍落"，这一拍有明确的动作终止感；
2. **定格加长到 0.28s 且不僵死**：悬停期间封面以 sine.inOut 缓缓下沉几度
   （-78°→-70°）——画面是"一本翻开的书立在书架上，封面微微沉降"，
   是活的一拍而非冻结；其他封面与书架此拍完全不动（节拍边界清晰）；
3. 定格结束才启动第三拍：邻卡散 + 扑面放大 + 书架退场同步推进。

验证（scrub 逐帧 + 数值断言）：0.65s 定格帧——封面 -74°/1.06、**其他封面全部可见、
书架完整**；1.05s 放大帧——封面 1.5 倍扑面、邻卡已淡出；终态与返回路径零报错 ✓。
通用教训：**节拍时长低于约 0.25s 时人眼读不出"停顿"，分离等于没做**；
定格期间给目标以微动（沉降/呼吸）可避免被读作卡顿。

## 十二、最终定稿（同日）：翻开与放大同步进行（一次复合运动）

用户再次澄清真实意图："我的意思是翻开动画和放大是一起进行的，现在的动画还是先翻开后变大"
——回顾全程，最初那句"打开动画和放大动画是同步的"本就是**需求**（要同步），
被误读为对"两者同时发生"的抱怨，于是先做了节拍分离、又做了节拍加强，方向反了。

定稿：**删除所有分段/定格，旋转与缩放写进同一条 tween**——
封面一边向外掀开（rotationY 0→-78°）一边扑面放大（scale 1→blowScale），
同一时长（0.85s）、同一起点、同一条缓动，运动途中永远是"半掀开+半放大"的复合姿态；
邻卡散/书架退场/交棒/记录表落定照旧衔接。返回路径本就对称（缩回+转回同时进行），
仅把起点姿态对齐为 -78°。

验证（scrub 数值断言）：运动同一时刻读到 **-20° 与 3.1 倍并存**（复合成立）、
-33° 与 4.5 倍并存；终态与返回路径零报错 ✓。

**教训记录：用户说"XX 和 YY 是同步的"时，先确认这是抱怨（同步发生但应分开）还是
需求（应当同步但目前没有）——语义歧义时按需求理解并留一句确认，别默认是抱怨。**
