# [2026-09-19] 开发工作流 skill 化

- 类型：功能修改（开发工具链，不涉应用代码）
- 调整版本：V0.15.5（应用代码零改动，不升版本号）
- 状态：✅ 已完成并验证

## 调整背景

开发工作流此前散在三处：`AGENTS.md`「改动流程」只有四行骨架；`项目复盘/03_开发工作流.md` 是复盘叙述（六步+过关标准，但夹在面试材料里）；每次改动靠 AI 自觉把两者拼接起来——触发不稳定、细节易漏（尤其是"方案分诊三列"和"收尾核对清单"这两步）。

## 调整后行为

工作流沉淀为**项目级 ZCode skill**：`.agents/skills/dev-workflow/SKILL.md`。用户提出任何改/修/加/优化请求时自动触发，也可 `/skill dev-workflow` 手动调用。内容为六步流程，每步带过关标准，末尾附收尾核对清单：

1. 需求澄清 + 方案分诊（能用的/用不上及原因/暂时不做及原因）
2. 先读代码再改（答得出"连带影响哪几处"才动手）
3. 小步实施（一次改动一句话能描述）
4. 三重自检（node --check → tests/run-tests.js → 浏览器冒烟 + 结构审计）
5. 文档沉淀（四个文件夹按性质归档，YYYY-MM-DD_标题.md，≤300 行）
6. 登记 + 版本 + 提交（目录.md 加行 → 导航版本表 → git commit 带版本号与缘由）

## 具体改动

- 新增 `.agents/skills/dev-workflow/SKILL.md`（约 70 行）
- 两轮子代理测试后修订 6 处含糊点：
  1. 纯 CSS/HTML 改动的检查替代（以页面健康关代替语法关）
  2. 半途接手"改动已写完"的任务时，第 1–3 步缺了就补
  3. minor/patch 判据收紧（minor 仅限从零新增的功能模块）
  4. 结构审计覆盖范围扩到 CSS
  5. 正文小节措辞与各文件夹模板统一（核心内容固定、字段按模板）
  6. 🔄/✅ 状态判据（视觉质感/动效手感类，自动化通过也只能标 🔄）

## 验证结果

- 两个只读子代理实测：
  - **测试①**（bug 报告类："页眉条数切换不刷新"）：正确走到第 2 步——先读 app.js 结构注释、穷举 `records` 全部 9 个写入点、答出"连带影响 5 处消费方"；归档判断为 bug修复文档、版本 patch+1、提交格式全对；未瞎改代码（且证实当前主链路并无此 bug，需向用户确认具体位置）。
  - **测试②**（CSS 改动收尾类）：正确产出第 4–6 步完整清单（功能修改文档归类 / patch+1 / 提交格式），并主动暴露 7 个含糊点，其中 6 个已回写进 skill。
- skill 为纯 Markdown，无 JS 改动，`node --check` 不适用；应用零改动，未跑冒烟。
- 通用版实测（同日）：在临时 Python 命令行项目（无测试/无文档体系/无 git 的三文件裸项目）上，子代理正确产出适配表——语法关自动降级为 `py_compile`、冒烟当最强门禁、文档归宿缺失→问用户而非臆造、无 git→如实上报；分诊三列/影响面/计划全齐。暴露 6 个通用性含糊点（无 git 降级出口、运行形态按 CLI/库/Web 映射、交互式入口需喂 stdin、检查工具的文件副作用、空约定时的保守默认红线、一次性项目轻量化），已全部回写通用版。

- **通用版**（用户级 `~/.agents/skills/dev-workflow/`）：六步骨架 + 新增"第 0 步 项目适配"——约定来源/验证关卡/文档归宿/版本提交约定四问，现场得出本项目适配表；配 `references/example-mozhang.md`（墨账填好的适配表）作实例。任何项目可用。

维护规则（已写进两份文件）：改流程骨架先改通用版，再同步项目版；项目细节只在项目版改。
